# BarClimb Decision Log

These are durable pre-build decisions. Supersede explicitly; do not silently delete.

- **NextGen-first:** v1 is the national NextGen UBE product. Jurisdiction add-ons are dormant future components, not v1 UI. V1 onboarding does not ask for jurisdiction, and recommendations, analytics, assessment generation, and readiness must neither require nor depend on it.
- **Assessment intelligence:** deterministic planning/specification precedes AI generation; raw first-pass AI is never learner-visible.
- **Complete coverage:** official NCBE scope manifest, not question count, defines curriculum completeness.
- **Schema-driven assessment UI:** AI composes only registered presentation/resource/response components.
- **Learning network:** public responses may become network nodes with threaded discussion, educational signals, qualified views, username identity, Circles, reputation, and sharing. Generic Like/Dislike and infinite social feeds are excluded.
- **Private mastery boundary:** community popularity/reputation never changes readiness/mastery.
- **Native at coordinated launch (superseded 2026-08-20):** Web, iOS, and Android were originally required to become publicly available together. React Native/Expo remains the native architecture, but simultaneous public release is superseded below.
- **Commerce:** server-authoritative cross-platform entitlement; Stripe web, Apple iOS, Google Play Android.
- **Healthy engagement:** Momentum/meaningful achievements, not punitive streak loss or doomscrolling.
- **Repository memory:** the repository ZIP must be sufficient to resume with zero chat history.
- **Coverage assurance v2 (2026-08-13):** “Complete coverage” means complete coverage of the current published NCBE scope, not a raw question count or an unverifiable claim to every conceivable rule. The release proof requires checksum-verified official sources, literal scope manifest, bidirectional mappings, reviewed Rule Obligations, authority mappings, applicable official NCBE Sourcebook reconciliation, per-subject catalog certification, independently confirmed assessment coverage targets, launch seeding, and strict CI/release snapshots.
- **Coverage tagging cannot self-prove (2026-08-13):** an assessment counts toward inventory/learner coverage only when independent validation confirms the named scope/RuleObligation target is materially exercised; context-only/incidental tags never count.

- **Three-scenario canonical architecture (2026-08-13):** Visitor, Free, and Plus experiences use one assessment/curriculum/learner truth. Complex pages consume server-authoritative versioned projections (`HomeProjectionV1`, public private overlays, Search/Progress/Attempt/Grade/capability projections) instead of client-side recomputation.
- **Orchestration is domain state (2026-08-13):** Study Sessions, Review Queue, Suggested Review, Repair Plans, learner planning snapshots, Session Impact, anonymous discovery/claim, notifications, and community launch models are explicit backend contracts, not frontend-only dashboard state.
- **Capability-driven Plus (2026-08-13):** clients render effective capabilities from server entitlement rather than scattering Free/Plus conditionals. Plus never changes scoring/mastery/community rank and is ad/upsell-free globally while authenticated.
- **Personalized public pages stay private (2026-08-13):** canonical SSR/SEO content is identity-independent; signed-in learner status is hydrated through private no-store overlays and never enters shared caches, metadata, sitemaps, or link previews.
- **Sourcebook dependency correction (2026-08-13):** NCBE Sourcebooks are optional enhanced reconciliation only. Mandatory coverage uses official NCBE perimeter + authoritative law + lawful independent reconciliation; automation remains the core compiler path.

- **Capability-driven surface parity (2026-08-13):** a versioned client surface capability manifest gates activation of Home, Search, Review, Repair, overlays, community, creator analytics, and account surfaces across required launch clients; plan names do not become scattered UI business logic.
- **Provider-agnostic subscription domain (2026-08-13):** `billing.Subscription`/provider events are canonical across Stripe, Apple, and Google. Stripe-specific IDs/tables are implementation details, not the product subscription truth.
- **Orchestration lifecycle hardening (2026-08-13):** StudySession, RepairPlan, entitlement, anonymous claim, review acceptance, and notifications have explicit lifecycle/idempotency/security obligations; safe-boundary entitlement changes cannot destroy accepted in-progress work.
- **Repository kickoff complete (2026-08-13):** the committed `main` repository baseline is authoritative; Milestone 1 is the next implementation milestone, and future recovery must not repeat bootstrap copy/initialization steps.
- **M1.1 monorepo/toolchain (2026-08-13):** use npm workspaces with `apps/backend`, `apps/web`, `apps/native`, and platform-neutral `packages/*`. Web and native own separate presentation implementations; shared packages expose only portable contracts, types, tokens, validation, analytics-event envelopes, and feature-flag shapes.
- **Runtime baselines (2026-08-13, superseded by M1.1a):** the initial Node 22.13 and Expo SDK 55/React Native 0.83 selection, including the claim that SDK 57 necessarily required TypeScript 6, was incorrect and is retained only as decision history.
- **M1.1 database testing (2026-08-13):** PostgreSQL remains mandatory for real environments. In-memory SQLite is permitted only for isolated framework health tests; database-sensitive integration work must use PostgreSQL.
- **M1.1a runtime baseline (2026-08-13; Expo patch updated 2026-08-20):** use Python 3.13.15, Django 5.2.17 LTS, DRF 3.16.1, Node 24.19.0 LTS with bundled npm 11.17.0, React/ReactDOM 19.2.3, Expo SDK 57.0.15, React Native 0.86.2, and TypeScript 5.9.3. Expo's documented dependency-validation exclusion preserves the controlling TypeScript 5.x line; no spec amendment is required. Expo SDK patch updates may follow Expo's compatibility metadata when they do not alter the selected SDK, React Native line, or product architecture.
- **Deterministic Python locks (2026-08-13):** maintain exact direct inputs in `requirements*.in`; generate complete `requirements*.txt` locks with pip-tools 7.6.1 under Python 3.13.15 using hashes and stripped extras; CI and recovery installs must use `pip --require-hashes`.
- **PostgreSQL acceptance (2026-08-13):** retain isolated in-memory SQLite foundation tests, but run the backend CI acceptance path—including checks, built-in migrations, health, and readiness—against PostgreSQL 17 through `config.settings.postgres_test`.
- **Portable packages (2026-08-13):** shared TypeScript packages target ES2022 with no ambient runtime types. Per-surface ESLint rules reject DOM/Node globals, Node built-ins, and client-renderer imports in `packages/*`. A compiled-output contract remains deferred until required by a non-bundler consumer.
- **Native routing readiness (2026-08-13):** the current proof-shell destination buttons are not navigation parity. Native routing, universal links/app links, and device builds remain later Milestone 1 work; orientation is unrestricted.
- **M1.2 KVS durability boundary (2026-08-13):** Redis/Valkey-compatible KVS is shared ephemeral infrastructure for Celery coordination, cache, future rate limits/locks, and explicitly short-lived orchestration only. PostgreSQL remains the sole durable business authority; KVS loss may delay or repeat idempotent work but may not erase learner, assessment, curriculum, publication, billing, or entitlement truth.
- **M1.2 Celery delivery policy (2026-08-13):** Celery uses no result backend and ignores results by default. Global late acknowledgement, worker-loss rejection, and implicit autoretry are disabled; every future business task must explicitly define deterministic idempotency, bounded retries/backoff, and PostgreSQL transaction boundaries.
- **M1.2 environment topology (2026-08-13):** local, test, disposable review, persistent staging, and production are explicit settings contracts. Deployed environments fail closed on missing/malformed mandatory runtime configuration. Heroku topology is web + worker + release; beat is deferred until scheduled work exists.
- **M1.3 identity boundary (2026-08-13):** establish one minimal custom Django user before business migrations. Private normalized email plus Django password is login authority; normalized unique username is future public identity. Jurisdiction, real name, learner/profile, entitlement, curriculum, analytics, preferences, and reputation belong outside identity.
- **M1.3 auth protocols (2026-08-13):** Web uses same-origin Django sessions plus explicit CSRF and never JWT. Native uses a random opaque 30-day credential whose digest/lifecycle is authoritative in PostgreSQL and whose raw value is stored only in Expo SecureStore; password reset and logout revoke it. Verification/reset use provider-neutral delivery and one-hour, hashed, purpose-bound, rotating, single-use tokens.
- **M1.3 permission/rate boundary (2026-08-13):** server-side authenticated/admin/owner primitives precede future business roles. Free/Plus, sponsor, and moderation permissions remain deferred. Redis-compatible KVS holds only digested ephemeral auth-rate counters; it never becomes identity authority.
- **M1.3a action-credential transport (2026-08-13):** reset/verification credentials use canonical-Web URL fragments, are removed immediately with `history.replaceState`, and reach Django only in CSRF-protected POST bodies. They never belong in request paths/query strings, referrers, analytics, logs, errors, browser storage, or cookies.
- **M1.3a security generation and serialization (2026-08-13):** native issuance revalidates credentials while holding the user-row lock. Reset uses the same lock order, increments a durable authentication generation, and revokes active native rows; session validity also checks the generation and active user. This small server-authoritative mechanism covers concurrent reset and future security-wide invalidation without JWT/refresh-token expansion.
- **M1.3a durable authentication email (2026-08-13):** PostgreSQL `AuthEmailDelivery` UUIDs are the provider-neutral idempotency boundary. Creation and token rotation are atomic; Celery receives only the UUID; workers use leases and bounded retry; beat reconciles due rows every minute; raw action credentials are HMAC-derived only in worker memory from digest-verified derivation metadata and active/fallback signing secrets. Crash-after-provider-send may repeat the same link but never rotates it. Future SendGrid must bind provider idempotency to the delivery UUID.
- **M1.3a Heroku/KVS trust boundary (2026-08-13):** review/staging/production force HTTPS and trust forwarded protocol/address only behind the declared Heroku router topology. Client IP is the canonicalized rightmost router-appended `X-Forwarded-For` value with `REMOTE_ADDR` fallback. KVS remains ephemeral; authentication fails closed with generic 503 if rate-limit state is unavailable, while PostgreSQL identity/session/outbox authority is unaffected.
- **M1.3a native failure model (2026-08-13):** only authoritative 401/403 validation removes a restored native credential. Offline/5xx preserves it. SecureStore read/write/delete failures and server-revocation failure are distinct terminal UI states; logout never claims success when server revocation is unavailable.
- **M1.4 same-origin staging Web (2026-08-15):** Heroku/Gunicorn serves the built React client and `/api/v1` from one HTTPS origin. Vite proxy configuration is local-only; deployed Web rejects an alternate API base. Django serves stable auth entry paths for direct navigation and refresh without introducing CORS.
- **M1.4 credential links remain Web-completed (2026-08-15):** the native canonical-link resolver and OS-association skeleton are extensible to future app destinations, but verification/reset paths are excluded from Universal/App Link claims. Fragment credentials remain Web-memory-only until real signing/domain association has separate evidence.
- **M1.4 environment identities (2026-08-15):** local, staging, and production native builds have distinct schemes and bundle/package identifiers. Staging/production require explicit HTTPS API/Web origins; public client configuration never carries secrets.
- **M1.4 staging email proof (2026-08-15):** a validating, non-delivering sink is allowed only by explicit staging opt-in and rejected in production. It proves durable outbox/worker/beat behavior without converting SendGrid or any delivery provider to verified status.
- **M1.4 Heroku KVS TLS (2026-08-15):** TLS remains mandatory and certificate verification is the default. The persistent Heroku staging app alone opts into Heroku's documented self-signed KVS certificate handling; the flag must not be generalized to another provider without evidence.
